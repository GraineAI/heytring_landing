# Counting k from the referral activity event

## The ask

`/api/v1/calls/admin/referrals` should return **window-matched** redemption counts, derived
from the same per-person event the activity feed already shows as:

```
18/08/2026, 11:02:29   referral   Got a referral code
```

That event is per-person and timestamped, which is everything the current k is missing.

## Why the current k is wrong

Today `k_factor = redemptions / base_users` and the live card reads:

```
k-factor      0.347
redemptions   26        <- counted over a 90-day window
referring     6 of 75   <- the 75 is all-time activated users
```

The numerator is windowed and the denominator is not. That is not a coefficient — it drifts
whenever either window moves, and nobody reading the card can see why. The landing repo
states this caveat on the tile rather than silently correcting it, because both halves are
only measurable here in Apollo.

## What settles it first — one query

**Before any of this is built, confirm what the event actually means.** "Got a referral code"
is ambiguous and the two readings lead to opposite conclusions:

- **"I redeemed someone else's code"** (a referee) — this is the redemption event, and it is
  exactly what k needs.
- **"I was issued my own code to share"** — fires for every user at signup and is useless as
  a numerator.

The test is a count. Roughly 26–27 people should have it if it is the first; roughly 164 —
everyone — if it is the second.

```sql
SELECT count(DISTINCT user_id) FROM activity WHERE kind = 'referral';
```

If that returns ~164, stop: the event is the wrong one, and the redemption record lives
somewhere else. Everything below assumes it returns ~26.

## What to return

Add to the `/admin/referrals` payload:

```jsonc
{
  "redemptions_in_window": 26,     // events with kind=referral in the requested window
  "base_users_in_window": 0,       // users who COULD have referred during that same window,
                                   // i.e. activated on or before the window opened
  "k_window_matched": 0.0,         // redemptions_in_window / base_users_in_window
  "redemptions": [                 // optional but far more useful
    { "referee_user_id": "...", "referrer_user_id": "...", "at": "2026-08-18T11:02:29Z" }
  ]
}
```

The per-row form is worth the extra work. With `referrer_user_id` on each redemption you get
the two things the card currently cannot show honestly:

1. **A cohort k** — referrals generated by the people who joined in month N, within 30 days of
   their own join. That is the only k that is comparable month over month, because every
   cohort is measured over the same amount of its own life.
2. **A real concentration figure.** The card currently says "the top 10% of referrers bring
   69.2%", but there are six referrers, so a decile is 0.6 of a person. The landing repo now
   relabels that as the headcount it describes; with per-row data it can be the real thing.

## What not to do

Do not compute k from PostHog. `referral_redeemed` has fired **once** against Apollo's 26 —
the client event under-fires by roughly 26x. Apollo grants the reward, so a redemption exists
there by definition; PostHog only hears about it if the app remembered to emit it. Advice
built on the client number told us to build a share mechanic that already exists and works.

## Context

The projection built on k was separately wrong and is fixed in the landing repo (commit
`bdf7172`): Apollo returns `projected_users = base * (1 + k)^cycles`, which models every user
referring k people every cycle forever. A referral programme is a geometric series over
cohorts, `base * (1 - k^(n+1)) / (1 - k)`, and at k < 1 it converges rather than compounds —
115 people from today's base, not the 9,070 the old formula claimed. The landing repo
overrides the projection at the proxy and preserves Apollo's original under `apollo` for
comparison. Worth fixing at source so both agree.
